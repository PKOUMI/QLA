01

What actually changes

Everything a teacher can do today stays exactly as it is. What changes is where the data lives and who is allowed to reach it.

ConcernTodayAfter
Where marks liveThe browser that typed themPostgres in London
Using two devicesImpossible — separate copiesLog in anywhere
Clearing site dataLoses everything, silentlyLoses nothing
Sharing with a colleagueExport and email a fileSame school, same assessment
Who may send emailAnyone holding the shared keyA signed-in teacher, for their own class
Charging for itNo way toPlan on the organisation

The shared key is deleted, not moved

APP_SHARED_KEY exists because there was no other way to stop strangers using your email endpoint. It was always a stopgap: every customer would hold the same secret, and any of them could read it out of the browser and send email as you. Once requests carry a session, the API authorises the person, and the key comes out entirely.

The stack, and why each piece

Email Resend EU region available £0 → ~£16/mo
Marketing site Cloudflare Pages Edge £0
Payments Stripe, later UK entity 1.5% + 20p

Supabase is the load-bearing choice. It is Postgres — not a proprietary document store — so if you ever outgrow it, the data comes with you as ordinary SQL. It ships authentication, and critically it enforces access rules in the database rather than in application code. More on why that matters in section 05.

Nothing leaves the UK

Supabase offers a London region and your Vercel functions already run in lhr1. When a DPO asks where pupil data is stored and processed, the answer is London for both, with no transfer mechanism to argue about. That is a stronger answer than most edtech can give, and it is worth saying on the pricing page.

The app moves off GitHub Pages

Not for the sake of it. Serving the app from Vercel puts it on the same origin as the API, which means session cookies can be httpOnly — unreadable by JavaScript, so a cross-site scripting bug cannot steal a login. Tokens in localStorage, the alternative, can be. It also retires CORS configuration entirely, which has already cost you an evening.

04

Data model

Two changes of substance from today’s shape: everything hangs off an organisation, and pupils belong to the school rather than to one assessment.

Corrected: there is no classes table

An earlier draft of this plan gave each assessment a class_id. That was wrong, for two reasons that only somebody who has taught would catch.

An assessment is a script, not a class. One teaching group routinely splits across tiers — most of 10B sitting Combined Biology Foundation Paper 1 while four higher attainers sit the Higher paper. Those are two assessments drawing from one group, which a class-owned assessment cannot express.

Sets change through the year. A structural pupil-to-class link goes stale every time somebody moves group, and stale structure quietly corrupts everything downstream of it.

So: pupils belong to the organisation. Each assessment has an entry list — who actually sat this paper — drawn from the school’s roster. Setting up an assessment offers three ways to fill it: copy the entry list from a previous assessment and untick whoever is not sitting this one, import a CSV, or add by hand.

That handles the tier split exactly as it happens in a department: copy last term’s Biology entry, untick the four doing Higher, done. No structure to maintain, nothing to go stale, and nobody has to keep a class list in step with reality. 

-- Every row belongs to an organisation. There is no path to another's.
create table organisations (
  id         uuid primary key default gen_random_uuid(),
  name       text not null,                          -- "Northgate Academy"
  kind       text not null check (kind in ('school','trust','individual')),
  trust_id   uuid references organisations(id),        -- a school inside a MAT
  plan       text not null default 'free',
  created_at timestamptz not null default now()
);

-- Which teachers belong to which school, and what they may do.
create table memberships (
  user_id uuid not null references auth.users(id) on delete cascade,
  org_id  uuid not null references organisations(id) on delete cascade,
  role    text not null check (role in ('owner','admin','teacher')),
  primary key (user_id, org_id)
);

-- Pupils belong to the school. Not to a class, not to an assessment.
-- Sets change and tiers cut across them; the pupil is still the same pupil.
create table pupils (
  id           uuid primary key default gen_random_uuid(),
  org_id       uuid not null references organisations(id) on delete cascade,
  name         text not null,
  email        text,
  parent_email text,
  external_id  text,                            -- optional MIS / UPN reference
  group_label  text,                            -- "10B/Sc2" — a label, not a structure
  email_text   jsonb not null default '{}',      -- per-pupil wording
  created_at   timestamptz not null default now()
);

-- Identity within a school. Either key alone is enough to recognise
-- somebody on a re-import; names are never used for matching.
create unique index pupils_org_email on pupils (org_id, lower(email))
  where email is not null;
create unique index pupils_org_extid on pupils (org_id, external_id)
  where external_id is not null;

-- Who actually sat this paper. The Foundation entry and the Higher entry
-- draw different pupils from the same teaching group.
create table assessment_pupils (
  assessment_id uuid not null references assessments(id) on delete cascade,
  pupil_id      uuid not null references pupils(id) on delete cascade,
  position      int not null,
  primary key (assessment_id, pupil_id)
);

create table assessments (
  id               uuid primary key default gen_random_uuid(),
  org_id           uuid not null references organisations(id) on delete cascade,
  owner_id         uuid not null references auth.users(id),
  name             text not null,
  subject          text,
  paper_type       text not null default 'higher',
  blank_policy     text not null default 'incomplete',
  grade_boundaries jsonb not null default '[]',
  email_text       jsonb not null default '{}',
  settings         jsonb not null default '{}',      -- lock, chart choices
  locked_pin_hash  text,
  updated_at       timestamptz not null default now()
);

create table questions (
  id            uuid primary key default gen_random_uuid(),
  assessment_id uuid not null references assessments(id) on delete cascade,
  position      int  not null,
  number        text not null,                        -- "01.1", free text
  max_marks     numeric not null check (max_marks > 0),
  topic         text,
  reteach_url   text
);

-- NULL mark means NOT MARKED. It is not zero, and never becomes zero
-- by accident. The whole app depends on this distinction holding.
--
-- A mark hangs off the ENTRY, not the pupil, so taking somebody off an
-- assessment takes their marks for it with them — and leaves every other
-- assessment they sat untouched.
create table marks (
  assessment_id uuid not null,
  pupil_id      uuid not null,
  question_id   uuid not null references questions(id) on delete cascade,
  mark          numeric,
  primary key (assessment_id, pupil_id, question_id),
  foreign key (assessment_id, pupil_id)
    references assessment_pupils(assessment_id, pupil_id) on delete cascade
);

-- An audit trail. Schools will ask what was sent, to whom, by whom.
create table send_log (
  id            uuid primary key default gen_random_uuid(),
  assessment_id uuid not null references assessments(id) on delete cascade,
  sent_by       uuid references auth.users(id),
  sent_at       timestamptz not null default now(),
  recipients    int not null,
  succeeded     int not null,
  failed        int not null
);

The jsonb columns are deliberate. Grade boundaries, chart preferences and email wording are read and written whole, never queried across schools, and their shape is still moving. Making each a table would buy nothing and cost a migration every time the app changes.

Recognising the same pupil twice

This is the part that decides whether a school roster is a feature or a mess. When a CSV is imported in March, the app has to know that “A Stone” is the Amelia Stone already on the roster from September — otherwise the school accumulates three of her and progress over time becomes impossible.

Match onReliabilityUse it?
MIS / UPN reference Exact. Survives name changes, set changes, everything Yes, when the export has one
School email Unique per pupil in every school system worth the name Yes — the default
Name Two J Smiths in a year group. Names change Never, on its own

So the CSV template gains one optional column, Pupil ID, which data staff can fill from the MIS export. When it is there, matching is exact. When it is not, school email does the job. When neither is present — a pupil with no email address — the import creates a new record and says so, rather than guessing from a name and silently merging two children.

Nothing new is asked of anyone

You already collect school email, and you said data staff can pull whatever is needed. Pupil ID is optional, so a teacher exporting a quick list from memory is not blocked, while a department whose office runs the export properly gets exact matching for free.

The import screen shows what it decided before anything is written: 62 pupils recognised, 3 new, 1 needs checking, with the ambiguous one offered for a human decision. Same principle as the rest of the app — show the working, then ask.

05

Keeping one school out of another’s data

This is the part that has to be right. Everything else is inconvenience if it breaks; this is a notifiable data breach involving children.

The usual approach is for the application to add where org_id = ... to every query. It works until the day somebody forgets one — and that somebody is me, on a Friday, adding a feature. Postgres can enforce it instead, underneath the application, where forgetting is not possible. 

alter table assessments enable row level security;

-- A teacher sees an assessment only if they belong to its organisation.
create policy "read own org" on assessments for select
  using (org_id in (
    select org_id from memberships where user_id = auth.uid()
  ));

-- Child tables inherit the rule through their parent.
alter table marks enable row level security;

create policy "read own org" on marks for select
  using (question_id in (
    select q.id from questions q
    join assessments a on a.id = q.assessment_id
    where a.org_id in (
      select org_id from memberships where user_id = auth.uid()
    )
  ));

With those in place, select * from marks run by a signed-in teacher returns their school’s marks and nothing else — even though the query asked for everything. A bug in my code becomes an empty result rather than a breach.

Moving pupils to the organisation actually simplifies this: the pupils table carries org_id directly, so its policy is a single membership check with no joins at all.

Two ways to defeat this, both avoidable

The service_role key bypasses RLS entirely, by design. It must live only in Vercel’s environment variables, never in anything sent to a browser, and be used only where a request genuinely acts for the system rather than a person.

And RLS is off until switched on per table. A new table added later with no policy is readable by anyone with an account. That belongs on a checklist, not in my memory — so the test suite will assert that every table has RLS enabled, and fail the build if one does not.

06

Signing in

A teacher types their school email. They get a six-digit code, or a link, and they are in. No password to choose, forget, reuse from another site, or have leaked in somebody else’s breach — and it proves they control a school address, which is the thing you actually want to know.

  1. Teacher enters a.okafor@school.sch.uk.
  2. Supabase emails a one-time code, valid for a few minutes.
  3. They enter it; the API sets an httpOnly, Secure, SameSite=Lax session cookie.
  4. Every later request carries it automatically. JavaScript cannot read it.
  5. First sign-in only: they name their school, which creates the organisation and makes them its owner.

Colleagues join by invitation from an owner or admin, which is also how a school’s plan covers them. Nobody joins a school by guessing its name.

One exception, because the alternative is colleagues unknowingly duplicating each other. If somebody signs up on an email domain that already has an organisation, they are told so — “Northgate Academy already uses EveryPupil” — and offered a button that sends a join request to an admin. The admin still decides. Nothing about the school is revealed beyond the fact that it has an account.

Microsoft SSO, when a trust asks

Schools run on Microsoft 365 or Google Workspace, and “sign in with your school account” converts far better than any email flow. It is also more setup, and needs IT to consent to an app registration. The database does not care which way somebody authenticated, so adding it later changes the sign-in screen and nothing else. Worth doing when the first trust asks, not before.

07

What happens to work already done

Your GCSE Science assessment and anything else in a browser today does not have to be re-entered. js/storage.js was written behind a repository interface for exactly this — list, get, save, remove — so a Supabase implementation slots in beside the localStorage one.

On first sign-in the app finds any local assessments and offers to upload them. The local copy is left alone until the upload is confirmed, so a failed import cannot lose anything. The existing JSON export is the fallback if a browser has already been cleared.

The paywall is collaboration, not volume

Any per-account allowance can be farmed by making more accounts: eight teachers, eight free accounts, 280 pupils between them, nobody pays. Tightening the cap does not fix that — it only makes the free tier useless to the solo triallist it exists for.

What a department actually wants is one person setting up the Biology paper and everyone else using it, results in one place, one invoice, one admin, a DPA. Eight disconnected free accounts cannot do any of that at any size. So the free tier is deliberately solo: no invitations, no shared papers, no school view. Farming it costs a department every feature that made them want it.

The domain hint in section 06 closes most of what is left, and improves the product either way.

Email caps exist to protect your sending reputation as much as your margin: one misconfigured trial account sending thousands of bounces would damage deliverability for every customer.

Stripe comes last, and only once schools are actually asking to pay. It is a subscription per organisation, a webhook that sets plan, and an invoice route for the many schools that cannot pay by card. Building it before anyone wants to buy is the classic way to spend three weeks on nothing.

09

What the law and the buyers require

None of this is code, all of it blocks a sale, and most of it is cheap if started early and expensive if left until a trust asks.

ObligationWhyWhenCost
ICO registration Legally required to process personal data as a business Before the first real school ~£40–60/yr
Data Processing Agreement The school is the controller, you are the processor. They cannot lawfully use you without one Before the first real school £0–500
Sub-processor list Supabase, Vercel, Resend, Stripe — named, with what each handles and where With the DPA £0
Privacy notice The /privacy/ page the site already links to Before launch £0
Retention & deletion 30 days on cancellation, and pupils auto-removed after 24 months idle. Both must be real processes, not intentions With accounts £0
DPIA support pack The school writes it; giving them the technical answers wins deals First trust conversation £0
Cyber Essentials Many MATs will not buy without it Before selling to trusts from ~£300

Two things to be careful about saying

There is no such thing as being “GDPR certified”. Claiming it marks you out as someone who has not done the work. Describe what is actually true — data in London, these sub-processors, this retention period, a DPA on request — which is more persuasive anyway.

And the pricing page currently promises UK hosting and 30-day deletion. Both become true when this plan ships. Until then the data-protection section says so plainly, and it needs updating the day it changes — in whichever direction.

Worth registering with the ICO early regardless: it is cheap, it takes ten minutes, and it is the first thing a school business manager checks.

10

Build order

Each phase leaves the app working. Nothing here is a big-bang rewrite, and you can stop after any phase and still have something usable.

1

Foundations

~1 week · nothing visible changes

Create the Supabase project in London. Write the schema and the RLS policies. Move the app from GitHub Pages to Vercel so it shares an origin with the API. Add the test that fails the build if any table has RLS switched off.

Done when the app works exactly as now, served from Vercel, with an empty database behind it and every table locked down.
2

Sign in

~1 week · first visible change

Email-code sign-in, the session cookie, creating an organisation on first use, and inviting colleagues. The app still reads and writes local storage — this phase only establishes who someone is.

Done when you can sign in on your laptop and your phone and see the same account, even though the data is still local to each.
3

Data moves to the database

~1–2 weeks · the real work

The Supabase repository behind the existing storage interface, the school pupil roster with entry lists and copy-from-previous, the matching rules on import, and the one-time offer to upload anything already in the browser. Delete the shared key and switch the email API to authorise by session.

Done when marks entered on one device appear on another, and the sample GCSE assessment survives a round trip intact.
4

Plans, limits and the paperwork

~1 week

Enforce the free-tier limits. Build account deletion, export, and the scheduled job that removes pupils idle for 24 months, so the promises on the pricing page and in the privacy notice are real. Write the privacy notice, the DPA and the sub-processor list. Register with the ICO.

Done when a school could trial it and their DPO could be answered without you writing anything new.
5

Taking money

~1 week · only when someone wants to pay

Stripe subscriptions, the webhook that sets the plan, and an invoice route for schools that cannot use a card. Deliberately last.

Done when a school can buy without you touching the database by hand.

Phases 1 to 3 are the ones that matter. After phase 3 you have a product a school can genuinely trial; phases 4 and 5 turn a trial into a customer.

11

What worries me

  • RLS on a table I add later. The likeliest route to a real breach, because it fails silently and looks fine. Hence the build-failing test, not a note in a document.
  • Losing a teacher’s marks during the upload. Mitigated by never deleting the local copy until the upload is confirmed — but a half-finished import at 10pm in November is exactly the moment a teacher stops trusting you.
  • Duplicate pupils on the roster. The failure mode of a school-level roster: import without emails a few times and one child becomes four records, which looks like nothing is wrong until somebody wants progress over time. Hence matching on identifiers only, and showing what the import decided before it writes.
  • Moving pupils out of assessments spreading. It touches the marksheet, the CSV importer and the feedback engine. Smaller than the classes refactor it replaces, but still the phase most likely to overrun.
  • A roster is data held for longer. Pupils used to vanish when an assessment was deleted; now a school accumulates a register that persists. That needs a real answer on retention — see the question below — and it is exactly what a DPO will ask about.
  • Region is chosen once. A Supabase project’s region cannot be changed afterwards — only migrated to a new project. Selecting London at creation matters more than anything else on setup day.
  • Free-tier limits at Supabase. Free projects pause after a period of inactivity, which is fine while building and not fine once a school depends on it. Budget for the paid tier before the first real trial, not after.
  • Everything in section 09 is unbudgeted time. The DPA and the privacy notice are not code and will not write themselves at the weekend.

The one thing I need from you

Create the Supabase project. It is the only step I cannot do, and one part of it is irreversible.

  1. Sign up at supabase.com and create a project named everypupil.
  2. Set the region to West Europe (London), eu-west-2. A project’s region cannot be changed afterwards — only migrated to a new one. This is the single most consequential click of the setup.
  3. Save the database password it generates somewhere you will not lose it.
  4. From Project Settings → API, send me the Project URL and the anon public key. Both are safe to share — the anon key is designed to sit in a browser, and Row Level Security is what protects the data behind it.
  5. Do not send me the service_role key. It bypasses every security policy by design. Put it straight into Vercel’s environment variables and nowhere else — not a message, not a file, not the repository.

Still worth doing first

Get the marketing site live and show it to two or three heads of department you know. Their reaction to £195 and £495 will teach you more than a month of building, and phases 1 to 3 are far easier to justify once somebody has said they would use it.

Estimates assume part-time evenings and weekends and will move. The order is firmer than the durations: each phase depends on the one before it, and phase 5 should not start until a school has asked to pay.
